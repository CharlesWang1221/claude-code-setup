# 教材復盤

這個流程回答兩件事：這週我們的做事方法變了什麼，以及哪些變化已經有證據、可以拿去教別人。

它和另外兩個復盤分工，不互相取代：

| 復盤 | 看什麼 | 負責 |
| --- | --- | --- |
| 製作復盤（`docs/PRODUCTION_RETRO_LOG.md`） | 成品被退回的缺失與 SOP 修正 | 阿派、鐵雄、師傅 |
| 成析 T6（`podcast-performance-review`） | 播放成效 | 小渡 |
| 教材復盤（本 Skill） | 流程與方法的變化，轉成教材 | 小查特助室，老查親自給原話 |

## 開始前

1. 讀根目錄 `AGENTS.md`、`BRAND_CONTEXT.md`。
2. 確認時間：用 Asia/Taipei 判斷本週範圍，週一 00:00 到週日 23:59，週次用 ISO 週（例：`2026-W42`）。
3. 找到 Google Drive 本機掛載位置下的 `我的雲端硬碟/不標準答案/復盤內容/`。找不到或無法寫入就停下回報，不得改寫到 repo 或其他資料夾。公開 repo 只寫相對路徑，不記錄任何電腦的絕對路徑。
4. 讀該資料夾的 `README.md` 與 `教材索引.md`，知道現有分類與卡片，避免重複建卡。

## 步驟一：收集本週變化（唯讀）

依序讀以下來源，只取「做事方法改變」的部分：

- `git log --since="<週一> 00:00" --until="<下週一> 00:00"`：標題、說明與改動檔案。略過「自動同步」、依賴更新、純格式調整的 commit。
- `docs/RULE_CHANGELOG.md` 本週日期的列，特別是「觸發原因」欄：這是老查原話最接近的來源。
- `docs/PRODUCTION_RETRO_LOG.md` 與本週製作復盤：重複出現的缺失，常是流程要改的訊號。
- `docs/QUOTA_LEDGER.md`：額度、重做次數與工時的變化。
- `docs/RELEASE_EVIDENCE_REGISTER.md`：本週有沒有讓上週「尚待實測」的規則拿到平台讀回證據。
- 本機 `journals/` 本週日記（不在 repo，可能不存在）：只取工作方法的反思，家庭、孩子與私人生活不取。

## 步驟二：問老查三題（一次問完）

```text
【教材復盤｜YYYY-Www】這週請用口語回我三句就好，不想答可以跳過：
1. 這週最卡、最想罵人的一刻是什麼？
2. 哪個改變讓你最有感？（省了時間、少了焦慮、少守電腦都算）
3. 這週哪件事，你最想教給別人？
```

老查的回答照原話記錄，不潤飾。沒回答就寫「老查原話：未提供」，不得自行編寫感受或代替老查下結論。

## 步驟四：做成教材卡

一個「方法改變」一張卡。同一主題已有卡片時，在原卡「版本紀錄」追加，不另開新卡。

收錄門檻：改變了誰做、怎麼做、何時停或怎麼判斷其中一項。只是改錯字、搬檔案、改名稱的不收。

檔案：`復盤內容/教材/<分類資料夾>/<首次日期>_<主題>.md`。

### 固定分類

| 資料夾 | 收什麼 |
| --- | --- |
| `01_AI團隊與角色分工` | AI 角色怎麼設、權責怎麼切、誰能推翻誰 |
| `02_SOP與Skill設計` | 規則怎麼寫才會被遵守、母版與同步 |
| `03_品管與退件迴路` | 稽核、退件分級、錯誤怎麼回流改 SOP |
| `04_授權與發布自動化` | 人要在哪裡批准、哪些可以一次授權、平台讀回 |
| `05_額度與成本控管` | 模型分級、預算卡、重做上限、不耗 AI 額度的腳本 |
| `06_內容產線設計` | 節目、短片、長片的產線形狀、並行與審核節奏 |
| `07_跨電腦與工具環境` | 多台電腦、同步、路徑、工具安裝邊界 |
| `08_踩坑與失敗` | 做錯的事、看起來成功其實沒生效的事 |

新增分類需老查同意。一張卡只放一個主分類，其他相關分類寫在 `相關分類` 欄。

### 卡片模板

```md
---
標題：
分類：
相關分類：
成熟度：草稿｜已驗證｜可教
可公開範圍：可公開｜去識別後可公開｜僅內部
首次記錄：YYYY-Www
最後更新：YYYY-MM-DD
來源：commit 短碼、RULE_CHANGELOG 日期
---

# 標題：用一句話講改了什麼

## 原本怎麼做
具體場景，誰卡在哪裡、浪費了什麼。

## 改成什麼

## 為什麼改
觸發事件與老查原話。

## 結果與證據
沒有證據就寫「尚待實測」，並寫下要看什麼證據才算成立。

## 可以教的一句話
學員帶得走的原則，一句。

## 給學員的練習
一題，30 分鐘內能在自己的工作上做完。

## 適用／不適用

## 版本紀錄
- YYYY-MM-DD：
```

### 成熟度判準

- **草稿**：規則已改，還沒在實際案件跑過，或沒有讀回證據。
- **已驗證**：至少一次實際案件跑過，有檔案、log 或平台讀回能指出結果。
- **可教**：已驗證，而且有前後對比（時間、次數、額度或錯誤數），加上練習題能讓外人照做。

「尚待實測」的規則一律是草稿，不得在工作坊當成已證實的方法。被推翻或回滾的做法不刪卡，改放 `08_踩坑與失敗` 或在原卡寫明失效原因，失敗本身就是教材。

## 步驟五：更新索引與回報

1. 更新 `復盤內容/教材索引.md`：每張卡一列，記分類、成熟度、可公開範圍、最後更新。
2. 某分類累積 3 張以上「可教」卡，在索引的「工作坊候選模組」標出來。要正式備課時交給小簡（`presentation-architect`）。
3. 回報老查，最多 5 行：本週新增幾張卡、升級幾張、哪個分類最接近可開課、下週要驗證什麼、有沒有需要老查決定的事。

## 停止線

- 不寫入公開 repo：週紀錄與教材卡只放 Drive。repo 只保存本 Skill。
- 去識別：不寫孩子可識別資訊、阿分未同意公開的內容、帳號、token、API key、未公開合作或客戶名稱。可公開範圍不確定時標「僅內部」。
- 不編造：數字、工時、前後對比必須來自檔案或老查原話，查不到就寫「無資料」。
- 品牌：教材語氣不販賣焦慮，不寫「不學就落後」「月入幾萬」。對外發表前仍要過阿維。
- 寫作：遵守 `AGENTS.md` 反 AI 味規則，原話保留口語。
