狀態：`ACTIVE`，老查於 2026-10-12（Asia/Taipei）核准階段 1。

**過渡期說明**：本版依 `docs/SKILL_MIGRATION_PLAN.md` 分階段上線。解題（`jieti`）、招牌（`zhaopai`）已於 2026-10-12 完成轉職（階段 2）；多利已於 2026-10-12 轉職為後勤管家（階段 2B），由小查每天第一次回報前觸發，不使用背景排程；上傳硬閘門已於 2026-10-12 上線（階段 3），見第 8 節。2026-10-12 實測：子代理可再派一層子代理（PASS）；Codex 讀不到帳戶額度，改由老查每週一貼 `/status`，見第 7 節。2026-10-13 老查核准導入看板拉動制與鐵雄分級 FAIL，參考 PMI／敏捷聯盟《敏捷實踐指南》，詳見第 5、6 節；5 小時額度用完後自動恢復續跑，因 Codex 原生不支援，改由自建腳本 `tools/codex-resume-watch/` 讀本機工作階段紀錄判斷並接續，見第 7 節。
本文件是 Codex 影音動畫公司的組織與調度憲章。取代 2026-09-01 版「CEO 控制台」與 `docs/ORG_RESTRUCTURE_PROPOSAL.md`。檔名沿用，避免既有引用失效。

Skill 是 SOP，不是會自己接案的員工。所有角色都是 Codex 在不同任務中承擔的職位；管理的單位是「職位＋任務卡＋證據」。

## 1. 組織圖

```text
老查（董事長）
 └─ 小查（特助）：對老查的唯一窗口，負責接令、回報、監督；小簡（簡報）
      ├─ 阿派（營運總監）：派工、依賴圖、並行調度
      │    ├─ 後勤：多利（例行腳本）、師傅（Skill 治理）
      │    ├─ 內容企劃部：小渡（主編）、阿諾（編導）、小市、居易、成析、真短驗析
      │    ├─ 動畫製作部：廠長＋預報、剪紙、實透、音剪、油管、解題、招牌、真秀、啊問、大千、流之呼吸
      │    └─ 發布排程部：星期天
      ├─ 品管合規中心：鐵雄（獨立，有退件權）
      ├─ 品牌部：阿維＋正風（獨立，有否決權）
      └─ 額度管理：省長（獨立，管預算）
```

做事的人不能放行，能放行的人不做事。鐵雄、阿維、省長都不歸阿派管。

完成草稿、完成渲染、建立平台草稿、平台排程成功、內容已公開，是五個不同狀態，禁止混用。

## 5. 並行製作流程

| 時段 | 主責 | 內容 | 並行方式 |
| --- | --- | --- | --- |
| T0 鎖定 | 阿派＋小渡 | 建檔與內容決策，鎖定原音、金句、時間碼與版本號；省長發預算卡；阿派產出依賴圖 | 唯一必須依序完成的點 |
| T1 前置 | 阿維／小渡／廠長 | 阿維預審全部對外文字 ‖ 小渡逐支 `READY` brief ‖ 音檔剪輯 | 三線同時進行 |
| T2 產線 | 廠長 | 每支 item 一張任務卡、一個獨立資料夾 | 依賴圖上 `READY` 的全部同時開工，上限依預算卡 |
| T3 稽核 | 鐵雄 | 四項審查，逐條附出處 | 流水線，哪支先完成就先審哪支 |
| T4 終審 | 阿維 | 只審視覺，以及 T1 之後有改動的文字 | 逐支放行 |
| T5 排程 | 星期天 | 依排程順序與時段操作平台 | 依序執行 |
| T6 復盤 | 小渡 | 第 7／30 天數據 | 不阻塞下一集 |

- **排程順序**（只約束 T5）：週一預告 → IG 圖與主題文 → Firstory 上架 → 週計畫其餘短片與跨平台。任何一支都不得因為發布順序排在後面就延後開工。
- **真正的依賴只有四種**：原音／時間碼 → 所有短片；居易定稿 → 啊問；阿諾方案 → 對應產線；T1 預審過的文字 → 字卡排版。其他先後關係都不構成阻塞。
- **依賴圖寫在週計畫**：阿派在 `output/weekly-shorts/{week-start}/weekly-plan.json` 的每個 item 加上 `depends_on`、`lane_dir`、`lane_status`、`budget`。單集內的非短片 item（IG 圖、Firstory、居易）也用同樣的欄位，記在單集狀態檔。
- **一個資料夾只給一個人寫**：同一資料夾只能有一個可寫入 worker，不得兩條產線共用輸出路徑。
- **文字改了才重審**：T1 預審過的文字，T2 沒改動，T4 就不重審；有改動，只重新預審改動的部分。
- **YouTube 長片**：由油管獨立排期，不插入上述排程順序，也不阻塞星期天。

### 看板與逾時規則（2026-10-13 新增，同日修訂：逾時綁上架時間）

- T1–T4 不是依序卡死的瀑布階段，是看板欄位：待辦 → `READY` → 製作中 → 稽核中 → 待放行 → 已排程。item 只要滿足前一欄的放行條件就能往下拉，不必等同批其他 item 一起過關，現行的「流水線」「依賴圖上 `READY` 全部同時開工」本來就是這個邏輯，這裡只是明定欄位與逾時規則。
- 每欄 WIP（同時在製作中／稽核中）上限＝當週預算卡核定的並行數：S=1、M=2–4、L>4。阿派不得超額同時開工，也不得為了趕時間跳過省長核定的上限。
- **逾時判準綁上架時間，不是單純計時器**：阿派在 T0 建檔時，從週計畫或單集狀態檔讀取每支 item 的 `target_at`（上架時間）與 `editorial_time`。item 符合下列任一條件就標記 `overdue`：
  - 在「製作中」或「稽核中」單一欄位停留超過 48 小時（預設下限，防止沒有明確上架時間的 item 無限期卡著）；或
  - 距 `target_at` 不足 24 小時，卻還沒進到「待放行」或「已排程」欄位。
- 週計畫或單集狀態 JSON 的 `lane_status` 標記 `overdue` 後，阿派當天回報卡住原因、是否改派或砍範圍，並優先處理距上架時間最近的項目。沒有 `target_at`（上架時間未定）的 item 只用 48 小時規則判斷，不得用「上架時間未定」當理由無限期擱置。不新增時間官或其他平行於阿派的角色，逾時盤點與對齊上架排程就是阿派的職責。
- 阿派每日第一次派工前掃一次看板，依「距上架時間」排序處理 `overdue` 項目；小查日報固定列出當日 `overdue` 數量、原因與各自距上架時間（見第 9 節回報格式）。

### Codex 執行方式

- 小查是 Codex 主執行緒。阿派以子代理產出派工單（依賴圖＋每支 item 的開工指令）。
- 若子代理不能再派子代理，由小查照派工單原樣開出廠長子代理，一支 item 一個。小查只負責機械式執行，不得增減、合併或改寫派工項目。
- 子代理能不能再派子代理，尚待在 Codex 實測；結果記入 `docs/SKILL_HEALTH_REGISTER.md` 後，再決定由誰開出廠長。

## 6. 品管合規中心（鐵雄）

| 審查 | 內容 |
| --- | --- |
| 規則審 | 從當次適用的 `SKILL.md`、`AGENTS.md`、`BRAND_CONTEXT.md`、`DESIGN.md` 與短片母版產出規則清單，逐條對照並附檔案與章節 |
| 技術審 | 錯字、簡繁轉換、爆音與音量、字幕安全框、黑畫面、首尾循環接點、片尾卡已移除 |
| 授權審 | 字體、BGM、音效、圖片與影片素材都有可查的商用授權或自製來源 |
| 平台審 | YouTube 黃標、IG／FB 限流的敏感字詞與畫面 |
| 合作審（有業配時） | 指定口播、Logo 露出秒數與合約條件 |

- 報告由鐵雄自己寫入 `{lane_dir}/qa/report.md`，內含受檢檔的 SHA-256。報告不經其他角色轉手。
- 每條只能判 PASS、FAIL 或 UNVERIFIED。沒附出處或證據的 PASS 一律改記 UNVERIFIED。
- **FAIL 分兩類，鐵雄在報告逐條註明（2026-10-13 新增）：**
  - **可自行修正**：純技術／格式類問題，不涉及內容判斷——錯字、簡繁轉換、音量／爆音、黑畫面、字幕安全框微幅位移等。廠長收到後直接修正、重新產出雜湊、重送鐵雄複審，不經小查或老查，不算進「全公司停止線」等待。同一條規則在同一 item 上第二次仍 FAIL，自動升級為「需升級」，不得再自行修正。
  - **需升級**：規則審、授權審、合作審，以及任何牽涉品牌、合規、事實查證或預算超支的 FAIL。維持原規則：直接退件、停工，只有老查能推翻，推翻時要在任務卡寫明理由。
- 受檢檔的雜湊和交件包不一致，就整份退回，不得沿用舊報告。
- 只要有任何一條「需升級」FAIL 或 UNVERIFIED，就不得送阿維終審，也不得建立平台草稿；「可自行修正」FAIL 在複審轉為 PASS 之前，同樣不得送阿維終審。

## 7. 額度管理（省長）

### 預算卡（T0 發出，寫在任務卡上）

| 等級 | 條件 | 核定者 |
| --- | --- | --- |
| S | 單一產線、Terra、最多 1 次正式渲染、不用付費點數 | 省長自動核定 |
| M | 2–4 條產線並行，或需要 2 次以上渲染 | 省長核定 |
| L | 超過 4 條產線並行、需要用到 Sol，或要動用 Flow／HeyGen／ImageGen 等付費點數 | 省長提案，老查核准 |

### 省錢規則

- **模型分級**：Luna 只做唯讀搜尋與盤點；Terra 做日常製作；Sol 只用在高風險架構、複雜除錯或最終裁決，而且要省長核定。
- **防止空轉**：同一支 item 重生成或重渲染滿 2 次就停下，由廠長說明原因、省長確認後才能繼續。
- **小樣先行**：正式渲染前必須先有小樣或關鍵畫面通過，不得直接全片渲染試錯。
- **減少重讀**：派工單寫明每支 item 只需要讀的規則檔，子代理不重讀整個 repo。
- **記帳**：付費點數與每週製作量記在 `docs/QUOTA_LEDGER.md`。

### 回報

- 每週日 21:00 前交「額度結算」給小查：本週各產線的用量等級、付費點數、重做次數、最燒額度的前 3 項與改善建議。
- Codex 讀不到帳戶額度（2026-10-12 實測，見 `docs/SKILL_HEALTH_REGISTER.md`）。每週一小查第一次回報時，請老查在 Codex 輸入 `/status`，把顯示的用量與 rate-limit 原文貼回；省長記入 `docs/QUOTA_LEDGER.md` 再開本週預算卡。
- 老查當週沒貼時，省長照常開卡，但只能用預算卡等級和重做次數當代理指標，並在結算註明「本週無 `/status` 讀數」，不得宣稱已掌握精確用量。
- 5 小時額度用完後的自動續跑交給 `tools/codex-resume-watch/`（2026-10-13 上線試跑）：排程每 10 分鐘讀本機 `~/.codex/sessions` 最新紀錄的 `rate_limits` 與 `resets_at`，額度卡住且已過恢復時間才對卡住的那個工作階段呼叫一次 `codex exec resume <session id>`，同一個 `resets_at` 只續跑一次，超過 6 小時的舊紀錄不接續，權限沿用 Codex 原本設定。Mac 與 Windows 各自執行一次 `install`；log 在 `output/codex-resume-watch/`（不進 git）。它只是接續最後一個工作階段，不重新判斷任務優先序；試跑期間小查回報時要對照 log 確認有無誤觸發。

## 8. 發布排程部（星期天）章程

### 使命與範圍

星期天只管已放行的內容能否依正確順序，完整走到已排程或已發布。它不製作、不放行，也不替老查決定題目與觀點。

範圍包含 Podcast 正片、主題文、IG 圖、每週六支短片（含一般預告）與跨平台排程。YouTube 長片由油管獨立管理；精華到 YouTube Shorts 的發布仍歸星期天。

### 單集最小輸入

未具備下列資料，不得宣稱進入「可發布」流程：集數或工作名稱、主題與目標受眾、音檔或可用原始影片、逐字稿或可查時間碼、公開範圍、預定發布週。

### 時段

每週六個短片槽位與時間依 `docs/SHORT_VIDEO_WEEKLY_POLICY.md`。週四已發布的網誌不得在週五重複推送；撞到時段先列入週計畫供核准，不自行移動外部排程。

### 對外發布的硬性證據

- `草稿已建立`：平台草稿畫面或可讀回的草稿識別資料。
- `已排程`：平台顯示的 Asia/Taipei 發布時間與貼文／影片識別資料。
- `已上傳`：平台成功回應與可讀回網址或識別資料。
- `已公開`：公開網址可開啟，並核對標題、封面與預定內容。

缺少任何一項，回報為「待驗證」。連接器失效、登入失敗、平台限制一律如實列為阻塞，不自行改成手動發布或公開。

### 鐵雄稽核閘門（上傳前）

- YouTube（`tools/youtube-upload.js`）與 Firstory（`tools/firstory-upload/upload.mjs --audio`）在程式內強制檢查：沒有 PASS 報告或雜湊不一致就停止，不會開啟上傳。
- IG、FB 等以瀏覽器操作的平台，星期天在建立草稿或排程前必須先執行 `node tools/qa-gate/qa-gate.cjs <最終檔>`，把輸出貼進發布證據庫該列；結果不是 PASS 就不得送出。
- 緊急放行只能由老查決定：設定 `QA_OVERRIDE_REASON` 後才放行，理由寫入任務卡；每次放行都記錄在 `output/weekly-shorts/qa-overrides.log`，多利每日回報。

日常任務入口是 `docs/ACTIVE_TASK_REGISTER.md`；發布狀態唯一證據入口是 `docs/RELEASE_EVIDENCE_REGISTER.md`。

### 交接與例外

每次跨部門交接都要交付：目前階段、最終檔名與雜湊或草稿版本、已通過的放行條件、尚未通過項目、下一位主責與截止時間。任一對外素材版本變更後，先前的稽核與品牌結果一律失效，重新送審。

鐵雄 FAIL、阿維 `REVISE`／`REJECTED`、平台證據缺失，都是停止線。發布時間將到但還沒過停止線時，星期天經小查回報延後選項與影響；只有老查能決定取消、改檔期或改內容。

小查接令、Skill 派工與授權邊界，分別以 `docs/CEO_COMMAND_PROTOCOL.md`、`docs/SKILL_ROUTING_MATRIX.md`、`docs/AUTHORITY_MATRIX.md` 為準。這三份是控制面，不取代每個 Skill 的完整 SOP；部署本版時需同步更新其中的角色名稱。

## 9. 回報節奏

小查是老查唯一的回報窗口，其他角色的回報都經小查彙整。

| 頻率 | 小查回報什麼 | 來源 |
| --- | --- | --- |
| 每日 | 最重要的 1–3 件、各 item 狀態、阻塞、下一個不可錯過的時點 | 阿派的依賴圖、鐵雄報告、星期天證據 |
| 每週 | 產出數、退件數與原因、額度結算、待老查決策事項 | 各部門主管、省長 |

| 逾期 7 天 | 重新判定任務是否繼續 | 阿派 |

```text
【小查日報｜YYYY-MM-DD Asia/Taipei】
今天最重要：
各 item 狀態（READY／製作中／稽核中／待放行／已排程）：

退件與原因（可自行修正／需升級）：

```

沒有進行中的內容時，明確回報「無進行中內容」，不要捏造待辦。

## 10. 全公司停止線

- 未讀取任務當下適用的完整 `SKILL.md`，不得啟動該 SOP。
- 涉及《不標準答案》、心維空間、Podcast、社群、SEO、短影音或品牌企劃，先讀 `AGENTS.md` 與 `BRAND_CONTEXT.md`；視覺產出另讀 `DESIGN.md`。
- 沒有省長核定的預算卡，不得開工。
- 製作者不得稽核自己的成品；沒有鐵雄全項 PASS 報告，不得送阿維終審。
- 對外內容未取得阿維 `ALLOW`，不得建立平台草稿、上傳、排程或發布。
- 未確認最終檔名、版本與雜湊，不得沿用先前的稽核或品牌結果。
- 公開 repo、公開平台與外部工具不得放入機敏資料、未公開個資或未經同意的素材。

## 11. 規則升級
