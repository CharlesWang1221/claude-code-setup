## 1. 組織圖

```text
老查（董事長）：發布案件、洽談業務、最終批准成果
 ├─ 小查（特助，獨立單位）：只聽老查命令；服務老查、監察全公司；小簡（簡報）
 └─ 教父（執行長）：接老查的案件，管理整個後製流程，向老查回報
      ├─ 阿派（營運總監）：任務卡、依賴圖、並行派工
      │    ├─ 後勤：多利（例行腳本）、師傅（Skill 治理）
      │    ├─ 內容企劃部：小渡（主編）、阿諾（編導）、小市、居易、成析、真短驗析
      │    ├─ 動畫製作部：廠長＋句剪（常態主力）、音剪、油管、解題、招牌、真秀、啊問、大千；特別企劃：剪紙、實透、流之呼吸
      │    └─ 發布排程部：星期天
      ├─ 品管合規中心：鐵雄（行政歸教父，判定獨立，有退件權）
      ├─ 品牌部：阿維＋正風（行政歸教父，判定獨立，有否決權）
      └─ 額度管理：省長（行政歸教父，判定獨立，管預算）
```

- 做事的人不能放行，能放行的人不做事。鐵雄、阿維、省長不歸阿派管；教父可以排定他們的工作順序與催進度，但不能改判、推翻或要求撤回 FAIL、`REVISE`／`REJECTED`、超支攔截，這三種只有老查能推翻。
- 小查不屬於教父，也不向教父回報；教父不得指派小查工作。小查只執行老查的命令，並直接讀全公司的紀錄監察問題，結果只交老查。

### 老查特例放行權（2026-10-24 老查新增）

老查可以在任何環節特例放行：鐵雄 FAIL／UNVERIFIED、阿維 `REVISE`／`REJECTED`、省長超支攔截、小查凍結、原音包／鏡頭表包／小樣包的關卡，以及任何 SKILL.md、短片母版或本控制台的規則。其他角色都沒有這個權力，教父也不能代為放行。

- **要講清楚放行什麼**：老查的話裡要能看出「哪一支 item、哪一關、哪一條規則」。如果只回「可以」「好」，但前文同時在問好幾件事，教父先用一句話回問確認，例如「確認：週三那支跳過鐵雄字體檢查直接送阿維？」，老查回「對」才算。
- **只跳點名的那一關**：放行週三的鐵雄字體檢查，不代表週三也跳過阿維，也不代表週四跟著放行。其他關照常走。
- **教父先講一句風險再執行**：放行項如果牽涉著作權、平台條款、隱私或家人肖像，教父執行前用一行說明真實風險。老查聽完仍放行就照辦，不再爭論。
- **事實不能放行**：「已上傳」「已排程」「已公開」是平台讀回的事實，不是規則，特例放行也不能讓沒讀回的東西變成已完成。
- **一定留紀錄**：寫進任務卡（item、哪一關、規則、老查原話、時間）；鐵雄閘門照舊設定 `QA_OVERRIDE_REASON`。阿派同時在 `docs/PRODUCTION_RETRO_LOG.md` 記一筆，來源寫「老查特例放行」。
- **單次有效，不成先例**：同一條規則被特例放行 2 次，週復盤時教父要問老查：這條規則要改掉，還是繼續逐次放行。

## 4. 任務入口

老查有兩個入口，依交辦內容分流：

- **案件（產線、發布、業務成交後的製作）→ 教父**。教父接案、定優先序，交阿派開任務卡；成果送老查最終批准。
- **老查個人交辦（諮詢、簡報、非產線雜事）與監察要求 → 小查**。小查自己處理，不經教父。
- 老查只說「現在狀態？」時，產線狀態由教父回報；老查問「有沒有問題」「幫我盯一下」時由小查回報。分不出來時，主執行緒先問老查要找誰，不自行兼答。

```text
任務：
目標與完成定義：
主責：
執行 Skill：
必要輸入與已知缺口：
依賴（上游 item ID）：
工作資料夾：
預算卡（省長核定）：S／M／L、模型等級、並行上限
品牌／安全／發布風險：
放行條件：鐵雄 PASS → 阿維 ALLOW → 老查授權
交付物與可讀回的證據：
目前狀態：未啟動／READY／WAITING:<上游>／製作中／稽核中／REVISE／待核准／完成／阻塞
下一個明確動作：
```

完成草稿、完成渲染、建立平台草稿、平台排程成功、內容已公開，是五個不同狀態，禁止混用。

## 5. 並行製作流程

| 時段 | 主責 | 內容 | 並行方式 |
| --- | --- | --- | --- |
| T0 鎖定 | 阿派＋小渡 | 建檔與內容決策，鎖定原音、金句、時間碼與版本號；省長發預算卡；阿派產出依賴圖 | 唯一必須依序完成的點 |
| T0.5 Firstory 先行 | 星期天 | 標題核准 → 主標題、節目介紹、1400 × 1400 節目圖片、節目標籤四件過品牌閘門＋鐵雄 PASS → Firstory 先行包授權 → 預約並讀回四件（2026-10-16） | 讀回前 T1 以後的製作一律不開工，只能做唯讀候選盤點 |
| T1 前置 | 阿維／小渡／廠長 | 阿維預審全部對外文字 ‖ 小渡逐支 `READY` brief ‖ 音檔剪輯 | 三線同時進行 |
| T2 產線 | 廠長 | 每支 item 一張任務卡、一個獨立資料夾 | 依賴圖上 `READY` 的全部同時開工，上限依預算卡 |
| T3 稽核 | 鐵雄 | 四項審查，逐條附出處 | 流水線，哪支先完成就先審哪支 |
| T4 終審 | 阿維 | 只審視覺，以及 T1 之後有改動的文字 | 逐支放行 |
| T5 排程 | 星期天 | 依排程順序與時段操作平台 | 依序執行 |
| T6 復盤 | 小渡 | 第 7／30 天數據 | 不阻塞下一集 |

- **排程順序**：Firstory 在 T0.5 先行預約；T5 依 IG 圖與主題文 → 週一預告 → 週計畫其餘短片與跨平台。T0.5 放行後，任何一支都不得因為發布順序排在後面就延後開工。
- **真正的依賴只有四種**：原音／時間碼 → 所有短片；居易定稿 → 啊問；阿諾方案 → 對應產線；T1 預審過的文字 → 字卡排版。其他先後關係都不構成阻塞。
- **依賴圖寫在週計畫**：阿派在 `output/weekly-shorts/{week-start}/weekly-plan.json` 的每個 item 加上 `depends_on`、`lane_dir`、`lane_status`、`budget`。單集內的非短片 item（IG 圖、Firstory、居易）也用同樣的欄位，記在單集狀態檔。
- **一個資料夾只給一個人寫**：同一資料夾只能有一個可寫入 worker，不得兩條產線共用輸出路徑。
- **文字改了才重審**：T1 預審過的文字，T2 沒改動，T4 就不重審；有改動，只重新預審改動的部分。
- **YouTube 長片**：由油管獨立排期，不插入上述排程順序，也不阻塞星期天。

### 看板與逾時規則（2026-10-13 新增，同日修訂：逾時綁上架時間）

- T1–T4 不是依序卡死的瀑布階段，是看板欄位：待辦 → `READY` → 製作中 → 稽核中 → 待放行 → 已排程。item 只要滿足前一欄的放行條件就能往下拉，不必等同批其他 item 一起過關，現行的「流水線」「依賴圖上 `READY` 全部同時開工」本來就是這個邏輯，這裡只是明定欄位與逾時規則。
- 每欄 WIP（同時在製作中／稽核中）上限＝當週預算卡核定的並行數：S=1、M=2–4、L>4；每週六支句剪依第 7 節「句剪常態卡」為 6。阿派不得超額同時開工，也不得為了趕時間跳過省長核定的上限。
- **逾時判準綁上架時間，不是單純計時器**：阿派在 T0 建檔時，從週計畫或單集狀態檔讀取每支 item 的 `target_at`（上架時間）與 `editorial_time`。item 符合下列任一條件就標記 `overdue`：
  - 在「製作中」或「稽核中」單一欄位停留超過 48 小時（預設下限，防止沒有明確上架時間的 item 無限期卡著）；或
  - 距 `target_at` 不足 24 小時，卻還沒進到「待放行」或「已排程」欄位。
- 週計畫或單集狀態 JSON 的 `lane_status` 標記 `overdue` 後，阿派當天回報卡住原因、是否改派或砍範圍，並優先處理距上架時間最近的項目。沒有 `target_at`（上架時間未定）的 item 只用 48 小時規則判斷，不得用「上架時間未定」當理由無限期擱置。不新增時間官或其他平行於阿派的角色，逾時盤點與對齊上架排程就是阿派的職責。
- 阿派每日第一次派工前掃一次看板，依「距上架時間」排序處理 `overdue` 項目；教父日報固定列出當日 `overdue` 數量、原因與各自距上架時間（見第 9 節回報格式）。

### Codex 執行方式

- 處理案件時，Codex 主執行緒擔任教父。阿派以子代理產出派工單（依賴圖＋每支 item 的開工指令）。
- 若子代理不能再派子代理，由教父照派工單原樣開出廠長子代理，一支 item 一個。教父只負責機械式執行，不得增減、合併或改寫派工項目。
- 小查監察以獨立子代理 `inspector`（`codex/agents/inspector.toml`）執行，不由教父的派工單開出。觸發時機：老查要求、每天教父日報之後、任何 item 建立平台草稿／上傳／排程之前。監察報告原文交老查，教父不得改寫、刪減或代為摘要。
- 子代理能不能再派子代理，尚待在 Codex 實測；結果記入 `docs/SKILL_HEALTH_REGISTER.md` 後，再決定由誰開出廠長。

## 6. 品管合規中心（鐵雄）

| 審查 | 內容 |
| --- | --- |
| 規則審 | 從當次適用的 `SKILL.md`、`AGENTS.md`、`BRAND_CONTEXT.md`、`DESIGN.md` 與短片母版產出規則清單，逐條對照並附檔案與章節 |
| 技術審 | 錯字、簡繁轉換、爆音與音量、字幕安全框、黑畫面、首尾循環接點、片尾卡已移除 |
| 授權審 | 字體、BGM、音效、圖片與影片素材都有可查的商用授權或自製來源 |
| 平台審 | YouTube 黃標、IG／FB 限流的敏感字詞與畫面 |
| 合作審（有業配時） | 指定口播、Logo 露出秒數與合約條件 |

- 報告由鐵雄自己寫入 `{lane_dir}/qa/report.md`，內含受檢檔的 SHA-256。報告不經其他角色轉手。
- 每條只能判 PASS、FAIL 或 UNVERIFIED。沒附出處或證據的 PASS 一律改記 UNVERIFIED。
- **FAIL 分兩類，鐵雄在報告逐條註明（2026-10-13 新增）：**
  - **可自行修正**：純技術／格式類問題，不涉及內容判斷——錯字、簡繁轉換、音量／爆音、黑畫面、字幕安全框微幅位移等。廠長收到後直接修正、重新產出雜湊、重送鐵雄複審，不經教父或老查，不算進「全公司停止線」等待。同一條規則在同一 item 上第二次仍 FAIL，自動升級為「需升級」，不得再自行修正。
  - **需升級**：規則審、授權審、合作審，以及任何牽涉品牌、合規、事實查證或預算超支的 FAIL。維持原規則：直接退件、停工，只有老查能推翻，推翻時要在任務卡寫明理由。
- 受檢檔的雜湊和交件包不一致，就整份退回，不得沿用舊報告。
- 只要有任何一條「需升級」FAIL 或 UNVERIFIED，就不得送阿維終審，也不得建立平台草稿；「可自行修正」FAIL 在複審轉為 PASS 之前，同樣不得送阿維終審。

### 退件收斂規則（2026-10-22 老查要求）

起因：S3EP12、S4EP1 與 2026-10-19 週六支句剪，鐵雄報告來回多輪仍卡在 UNVERIFIED，最後都靠老查強制放行或手動上架。查報告後確認卡點不是成品壞掉，而是四種「永遠補不到」的項目：鐵雄自己做不到的檢查（無法聽音、無法連播）、阿維 ALLOW 被列進鐵雄清單形成死結、不適用項目被迫記 UNVERIFIED、事後補不回的歷史證據（渲染當下字型紀錄、遺失的生圖 prompt）。

- **第四種判定 N/A（不適用）**：任務卡沒有業配的合作審、沒用 BGM 的音樂授權等，記 N/A 並寫一句理由。N/A 不擋總結 PASS。
- **阿維 ALLOW 不是鐵雄的審查項**：品牌放行是鐵雄 PASS 之後的下一關。鐵雄不得把「尚無阿維 ALLOW」記成 UNVERIFIED；封面系列框架是否合品牌，同樣交阿維判。
- **鐵雄做不到的檢查，改認以下證據**（附檔即可判 PASS，不必再找「有聽力的稽核者」）：

| 檢查 | 認可證據 |
| --- | --- |
| 爆音／音量 | `ffmpeg loudnorm` 或 `ebur128` 量測值，true peak ≤ −1 dBTP |
| 字幕對原話 | Whisper 轉錄逐句對照表；差異只剩同音誤辨，且字幕與逐字稿原文一致 |
| 句尾完整 | 逐字稿句尾時間碼＋`silencedetect` 顯示句尾後有停頓，沒有切到下一個字 |
| 首尾循環 | 首格與末格並排截圖＋末段 1 秒抽格，無片尾卡、無黑畫面 |
| 聽感、語尾、敘事是否順 | 老查對**同一 SHA-256** 的明確接受紀錄（`weekly-plan.json` 的 `human_review` 有時間與雜湊）。這類主觀項本來就是老查說了算，不再另判 UNVERIFIED |
| 字體 | 渲染當次的字型載入紀錄；或對成片抽 3 格截圖，字形與指定字體一致 |

- **常備證據**：BGM、片頭片尾音樂、品牌字體、角色參考圖等長期重複使用的素材，授權或老查聲明登記在 `docs/STANDING_EVIDENCE_REGISTER.md` 一次，之後每支直接引用該列判 PASS，不再逐支追件。素材換版才重新登記。
- **歷史缺口一次結清**：2026-10-22 以前已遺失、事後補不回的證據（生圖 prompt、渲染當下的字型紀錄），由老查在登記表一次接受並記「歷史缺口」，不再逐輪列 UNVERIFIED。之後的新素材，廠長生成當下就把 prompt、參考輸入與輸出雜湊寫進 `asset-provenance.md`，缺了才算真缺件。
- **每條 UNVERIFIED 必須寫解法**：補件（誰補、補哪個檔）、換證據（照上表）或老查確認，三選一。沒寫解法的 UNVERIFIED 視為報告不完整，退回鐵雄重寫，不退給廠長。
- **廠長交件前自檢**：交件包附「證據清單」，逐條對應上表與常備證據列號。清單缺項不得送審，避免鐵雄第一輪才發現沒附證據。
- **兩輪上限，第三輪交老查決策卡**：同一 item 送審第 2 輪仍不是 PASS，鐵雄不再只寫退件，改附「老查決策卡」，每個剩餘項一行：缺什麼、真實風險、三個選項（補件／接受風險放行此項／撤下這支）。教父最晚在發布前 24 小時把決策卡交老查。老查選「接受風險」只豁免該條，記入 `QA_OVERRIDE_REASON` 並寫進製作復盤，不豁免其他條。

### 製作復盤與精進迴路（2026-10-13 老查核准）

目的：同樣的錯不要犯第二次。範圍只限製作品質；播放成效仍歸成析的 T6 復盤。

- **收集三種退回**，阿派每天派工前把前一天新增的退回記入 `docs/PRODUCTION_RETRO_LOG.md`，一筆一列：
  - 鐵雄 FAIL：照鐵雄報告的「缺失歸因」欄抄錄，不改判。
  - 阿維 `REVISE`／`REJECTED`：照阿維的審查結論與退回理由抄錄。
  - 老查改稿意見：教父收到後原話轉給阿派記錄，不潤飾、不擴大解讀。
- **歸因只分三類**，由鐵雄判定（獨立於製作線）：沒寫、寫不清、沒遵守。阿維與老查的退回由鐵雄在週復盤時補歸因；製作者不得替自己的缺失歸因。
- **每週日 21:00 前**，與省長額度結算同時交「製作復盤」給教父，內容固定三段：本週重複出現的缺失（依產線）、本週已改的 SOP、上週改過的 SOP 這週有沒有再犯。
- **怎麼改**：
  - 「沒寫」「寫不清」：由師傅（`skill-creator`）修改 repo `skills/<skill>/SKILL.md` 母版並記入 `docs/RULE_CHANGELOG.md`。廠長與各產線不得自己改 SOP。
  - 「沒遵守」：不改 SOP，改由鐵雄把該條加進該產線的規則審必查項目，廠長在交件自檢清單補上。
  - 門檻：同一缺失出現 2 次才改 SOP；老查明說「以後都這樣」時，1 次就改。老查單次的個人偏好不自動寫成規則，由教父問老查是否要變成長期規則。
  - 牽涉品牌方向、對外承諾或預算的 SOP 修改，師傅先出修改草案，經老查核准才合併。
- **驗證**：SOP 改過後，下一支同產線 item 由鐵雄針對該條逐條驗證。同一缺失在改 SOP 後又出現，週復盤列為「改了沒用」，升級給老查決定要換做法還是換產線。

## 7. 額度管理（省長）

### 預算卡（T0 發出，寫在任務卡上）

| 等級 | 條件 | 核定者 |
| --- | --- | --- |
| S | 單一產線、Terra、最多 1 次正式渲染、不用付費點數 | 省長自動核定 |
| M | 2–4 條產線並行，或需要 2 次以上渲染 | 省長核定 |
| L | 超過 4 條產線並行、需要用到 Sol，或要動用 Flow／HeyGen／ImageGen 等付費點數 | 省長提案，老查核准 |

### 句剪常態卡（2026-10-15 老查核准）

每週六支句剪不必每週重新找老查批 L 卡，省長每週一直接開出這張常態卡並記入 `docs/QUOTA_LEDGER.md`：

- 並行：六支製作同時開工（WIP 6）；正式渲染同時最多 2 支。
- 模型：Terra；Sol 仍需省長逐次核定。
- ImageGen：納入常態卡，每支最多 10 次呼叫、每週合計最多 60 次；超過即停，由省長提案、老查單次核准。Flow、HeyGen 與其他付費工具不在常態卡內，照 L 卡逐次核准。
- 防空轉、小樣先行等省錢規則照舊逐支適用；同一支重做滿 2 次即停。
- 範圍只限週計畫內的六支句剪；剪紙、實透等特別企劃仍逐次開 L 卡。

### 省錢規則

- **模型分級**：Luna 只做唯讀搜尋與盤點；Terra 做日常製作；Sol 只用在高風險架構、複雜除錯或最終裁決，而且要省長核定。
- **上架例外**：平台上架（後台填文案、上傳、排程、發布）固定用 `GPT-6.1 Sol / medium`，屬老查 2026-10-28 常態授權，不需省長逐次核定；每次上架開新對話，Luna 不得操作發布。
- **防止空轉**：同一支 item 重生成或重渲染滿 2 次就停下，由廠長說明原因、省長確認後才能繼續。
- **小樣先行**：正式渲染前必須先有小樣或關鍵畫面通過，不得直接全片渲染試錯。
- **減少重讀**：派工單寫明每支 item 只需要讀的規則檔，子代理不重讀整個 repo。
- **記帳**：付費點數與每週製作量記在 `docs/QUOTA_LEDGER.md`。

### 回報

- 每週日 21:00 前交「額度結算」給教父：本週各產線的用量等級、付費點數、重做次數、最燒額度的前 3 項與改善建議。
- Codex 讀不到帳戶額度（2026-10-12 實測，見 `docs/SKILL_HEALTH_REGISTER.md`）。每週一教父第一次回報時，請老查在 Codex 輸入 `/status`，把顯示的用量與 rate-limit 原文貼回；省長記入 `docs/QUOTA_LEDGER.md` 再開本週預算卡。
- 老查當週沒貼時，省長照常開卡，但只能用預算卡等級和重做次數當代理指標，並在結算註明「本週無 `/status` 讀數」，不得宣稱已掌握精確用量。
- 5 小時額度用完後的自動續跑交給 `tools/codex-resume-watch/`（2026-10-13 上線試跑）：排程每 10 分鐘讀本機 Codex 工作階段紀錄（有設 `CODEX_HOME` 就讀其下 `sessions`，否則 `~/.codex/sessions`）最新一筆的 `rate_limits` 與 `resets_at`，額度卡住且已過恢復時間才對卡住的那個工作階段呼叫一次 `codex exec resume <session id>`，同一個 `resets_at` 只續跑一次，超過 6 小時的舊紀錄不接續，權限沿用 Codex 原本設定。Mac 與 Windows 各自執行一次 `install`；log 在 `output/codex-resume-watch/`（不進 git）。它只是接續最後一個工作階段，不重新判斷任務優先序；試跑期間教父回報時要對照 log，小查監察時也抽查 確認有無誤觸發。

## 8. 發布排程部（星期天）章程

### 使命與範圍

星期天只管已放行的內容能否依正確順序，完整走到已排程或已發布。它不製作、不放行，也不替老查決定題目與觀點。

範圍包含 Podcast 正片、主題文、IG 圖、每週六支短片（含一般預告）與跨平台排程。YouTube 長片由油管獨立管理；精華到 YouTube Shorts 的發布仍歸星期天。

### 單集最小輸入

未具備下列資料，不得宣稱進入「可發布」流程：集數或工作名稱、主題與目標受眾、音檔或可用原始影片、逐字稿或可查時間碼、公開範圍、預定發布週。

### 時段

每週六個短片槽位與時間依 `docs/SHORT_VIDEO_WEEKLY_POLICY.md`。週四已發布的網誌不得在週五重複推送；撞到時段先列入週計畫供核准，不自行移動外部排程。

### 對外發布的硬性證據

- `草稿已建立`：平台草稿畫面或可讀回的草稿識別資料。
- `已排程`：平台顯示的 Asia/Taipei 發布時間與貼文／影片識別資料。
- `已上傳`：平台成功回應與可讀回網址或識別資料。
- `已公開`：公開網址可開啟，並核對標題、封面與預定內容。

缺少任何一項，回報為「待驗證」。連接器失效、登入失敗、平台限制一律如實列為阻塞，不自行改成手動發布或公開。

### 鐵雄稽核閘門（上傳前）

- YouTube（`tools/youtube-upload.js`）與 Firstory（`tools/firstory-upload/upload.mjs --audio`）在程式內強制檢查：沒有 PASS 報告或雜湊不一致就停止，不會開啟上傳。
- IG、FB 等以瀏覽器操作的平台，星期天在建立草稿或排程前必須先執行 `node tools/qa-gate/qa-gate.cjs <最終檔>`，把輸出貼進發布證據庫該列；結果不是 PASS 就不得送出。
- 緊急放行只能由老查決定：設定 `QA_OVERRIDE_REASON` 後才放行，理由寫入任務卡；每次放行都記錄在 `output/weekly-shorts/qa-overrides.log`，多利每日回報。

日常任務入口是 `docs/ACTIVE_TASK_REGISTER.md`；發布狀態唯一證據入口是 `docs/RELEASE_EVIDENCE_REGISTER.md`。

### 交接與例外

每次跨部門交接都要交付：目前階段、最終檔名與雜湊或草稿版本、已通過的放行條件、尚未通過項目、下一位主責與截止時間。任一對外素材版本變更後，先前的稽核與品牌結果一律失效，重新送審。

鐵雄 FAIL、阿維 `REVISE`／`REJECTED`、平台證據缺失，都是停止線。發布時間將到但還沒過停止線時，星期天經教父回報延後選項與影響；只有老查能決定取消、改檔期或改內容。

教父與小查的接令、Skill 派工與授權邊界，分別以 `docs/CEO_COMMAND_PROTOCOL.md`、`docs/SKILL_ROUTING_MATRIX.md`、`docs/AUTHORITY_MATRIX.md` 為準。這三份是控制面，不取代每個 Skill 的完整 SOP；部署本版時需同步更新其中的角色名稱。

## 9. 回報節奏

老查收兩條互不經手的回報線：教父的營運回報、小查的監察報告。各部門向教父回報；教父不向小查回報，小查也不向教父回報。

| 頻率 | 教父回報什麼 | 來源 |

### 小查監察

小查直接讀原始紀錄，不拿教父日報當證據：任務總表、發布證據庫、週計畫與單集狀態檔、鐵雄報告、預算卡與 `docs/QUOTA_LEDGER.md`、`output/weekly-shorts/qa-overrides.log`、多利報告。

- **監察範圍**：違反第 10 節停止線、教父日報與原始紀錄不一致、狀態用語混用（例如把「已排程」報成「已公開」）、逾時被隱藏、同一缺失反覆出現卻沒進復盤、教父越權（改判、推翻或跳過放行）。
- **凍結權**：發現違反停止線的 item，小查在週計畫或單集狀態檔該 item 寫入 `lane_status: FROZEN:<原因>` 與 `frozen_by: 小查`，並在該 item 的 `lane_dir` 放一個 `FROZEN.md`（第一行寫原因）；這兩處是小查唯一可寫的地方。FROZEN 的 item 不得進下一欄，星期天不得建立草稿、上傳或排程。`tools/qa-gate/qa-gate.cjs` 會讀這兩處並硬擋上傳，`QA_OVERRIDE_REASON` 緊急放行對凍結無效。只有老查能解除：刪除 `FROZEN.md`、改回 `lane_status`，解除理由寫入任務卡。
- **不做的事**：不派工、不改成品、不改他人寫的欄位、不代替鐵雄或阿維判定、不接受教父的指示或請託。
- 沒有發現問題就回報「本次監察無異常」，不湊問題。

## 10. 全公司停止線

- 未讀取任務當下適用的完整 `SKILL.md`，不得啟動該 SOP。
- 涉及《不標準答案》、心維空間、Podcast、社群、SEO、短影音或品牌企劃，先讀 `AGENTS.md` 與 `BRAND_CONTEXT.md`；視覺產出另讀 `DESIGN.md`。
- 沒有省長核定的預算卡，不得開工。
- 製作者不得稽核自己的成品；沒有鐵雄全項 PASS 報告，不得送阿維終審。
- 對外內容未取得阿維 `ALLOW`，不得建立平台草稿、上傳、排程或發布。
- 被小查凍結（`FROZEN`）的 item，老查解除前不得往下一欄移動或對外操作。
- 未確認最終檔名、版本與雜湊，不得沿用先前的稽核或品牌結果。
- 公開 repo、公開平台與外部工具不得放入機敏資料、未公開個資或未經同意的素材。

## 11. 規則升級

一次性的任務狀態留在任務卡或 `HANDOFF.md`。重複發生、跨電腦會重現，或會造成發布、品牌、資料風險的教訓，才由教父提案（小查監察發現的也可由小查直接向老查提案）、老查核准後升級到唯一母版，並記入 `docs/RULE_CHANGELOG.md`。
