# 2026-08-14 學習日記

## 今天做了什麼
接續昨天中斷的工作，把「多利」（每日 cloud routine 排程）的 Duoli Mailer 寄信全掛問題徹底查清楚並修好。一開始只是想改個環境變數，結果一路挖出 7 個疊在一起的根因：
1. Worker 收件人格式只吃陣列，但排程 prompt 寫成字串，被 400 打回
2. 7 支寄信排程的 Cloud environment 一直停在系統預設「Default」，根本沒切到早就建好的「Duoli Mailer」環境，token 沒被注入
3. Duoli Mailer 環境的 Network access 設成「Trusted」，把自訂的 Worker 網域擋在外面
4. Worker 端的 token 跟 claude.ai 環境變數版本不同步，回 401
5. Resend 用共用測試網域寄信，CC 給阿分（非帳號本人）被 403 拒收——後來發現帳號其實早就驗證過 `mail.beyond-ans.com` 這個子網域，換過去就解決了
6. 防重複 log 的 `git push` 一律 403——一開始猜是 GitHub App 權限問題，後來去 GitHub 網頁查證發現完全沒裝任何 Claude 的 App，判斷錯誤，真正原因是 claude.ai 平台規定「cloud session 的 git push 只能推回自己的 working branch」，最後改成幫 Worker 加一個 Cloudflare KV 端點取代 git，7 支排程全部改寫
7. 順手把新聞、AI創業案例、書籍摘要三支排程從每週改成每天，補上 CC

## 驚喜時刻
發現「GitHub 權限問題」這個第一直覺判斷是錯的，這是今天最有價值的一次翻案。查 `github.com/settings/installations` 才發現這個帳號根本沒裝任何 Claude App，逼自己回去查官方文件，才挖到「cloud session 的 git push 只能推回自己 working branch」這條平台規則——如果沒有去核對，可能就會建議去改一個不存在的權限設定，白繞一圈。這也提醒自己：遇到「權限問題」的直覺判斷，能查證的地方就先去查證，別急著下結論。

## 反思
今天也踩了兩個自己造成的坑：一是手動把中文字元轉成 `\uXXXX` unicode 編碼送出排程設定時，打錯了幾個字碼，一支排程的內容變成亂碼（「書喔吾聊」變成「書噴吳聲」），後來改成直接送出正常中文字元才修好——手動轉編碼這種事，能不做就不要做。二是今天沒有一次「寄信成功＋log 真的更新」的完整案例，因為自己重複測試同一支排程太多次，撞到 Resend 的 Idempotency-Key 快取，這不是新機制的 bug，但也代表今天的修復還沒有百分之百的端到端驗證，真正的驗收要等明天早上 8 點正式排程跑過才知道。
